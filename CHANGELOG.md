# Changelog

Dates are the day the work landed on `main`. Each release lists the schema
versions the runner reads and writes, because that changelog is what a user
sees in their upgrade pull request.

## Unreleased

Schemas: reads `*/1`, writes `*/1`.

### Fixed

- **Each setup workflow step is one runner command**, so the chain can be tested without a model or GitHub. A fixture walk feeds the writer deliberately bad answers (a broken shape, a dropped journey, a pasted password, a missed boot) and checks that the full reason is recorded, the step starts again, and a good round still opens the pull request.
- **Model answers that have a fixed shape are JSON, checked against that shape, and retried up to three times.** The journey list, the recipe's journey tests, the survey, and the classifier labels are filled into a written-down shape. Markdown is written by the program from the accepted JSON. An answer that still fails after three tries fails the step, and the shape errors are the reason.
- **A setup failure keeps its full reason.** The retry is given that reason. "The same failure twice" compares the real reasons, not a fixed sentence. Three failures in a row of one step also stops.
- **Every job that mints the GitHub App token, or that starts a model, checks credentials first** and names what is missing, instead of dying later on `Input required and not supplied: app-id`.
- **`bsf env apply` exits 0 after it saves the choices.** Names just marked to use count as present. A remaining wait is printed as information; queued jobs start only when nothing is waiting. The decide job no longer fails with "40 settings are waiting" after a successful save.
- **`bsf setup status` prints the current step, the last failure with its full reason, and what setup is waiting on.**

- **The factory's own tests run again.** Two unused imports failed the lint step, which skipped the test step on every merge for a day, and the tests drifted behind the code with nobody seeing it. The lint errors are gone, the tests match what the factory says and does, and `main` now refuses a merge whose checks have not passed.
- **Update mode says what it found again.** `bsf mine-corrections --merge-into` stopped printing how many candidates were new, already pending, or already decided. It prints that line again.
- **The setup workflow is valid again.** It read a secret in a job-level condition, which GitHub does not allow, so the whole file was rejected and setup could not start.
- **Setup does not start the settings check when the App is not installed.** The readiness check was looking at an empty checkout, and the job token cannot list Actions secrets, so a missing App id or model key looked fine and the next job died asking for `app-id`. The check now reads the fetched factory and treats an empty App id, App private key, or model key as not ready. The values themselves are never written into the script.
- **A recipe that drops a journey is refused, with the missing names as the reason.** The recipe step has to fill one entry per saved journey. Dropping one used to be patched over by restoring the heading and saving anyway; the writer now gets the shape error and tries again.
- **The prose cap fails growth, not a file that was already long.** Always-loaded conventions are still capped at 16 KiB, because every run reads them. The static check now fails only when a change made one of those files larger and left it over the cap. A file the owners already wrote, left untouched, passes, and setup is no longer told to split it.
- **One issue is one hardening item.** The "Harden this" form applies its label when it opens the issue, so GitHub sends `opened` and `labeled` together and intake made a work item for each: two cards on the dashboard, two hardening runs. Intake now counts the items it has just made as open for the events after them in the same batch, and an issue that already has hardening work does not get a second item from the label.
- **An issue waiting for a maintainer no longer says "queued".** Issues from people the factory does not trust get `factory:awaiting-maintainer` instead of `factory:queued`; accepting the issue swaps it for `factory:queued`, and a run starting removes both.

### Added

- **The conversation happens in seconds instead of minutes.** A brainstorm turn was a whole workflow run — a comment woke intake, intake requeued the item, a role started from scratch and built a sandbox it never used in order to ask one question. Three to five minutes a turn, which is correspondence rather than conversation. One job now stays alive for the whole exchange: the agent asks with `bsf brainstorm say`, blocks on `bsf brainstorm wait`, and a turn costs the model call. The conversation is the agent's own session, so a fourth question knows what the first three answers settled without anything being re-read.

  The poll is conditional, which is what makes it affordable. GitHub's guidance is explicit that a conditional request returning 304 does not count against the primary rate limit, so watching an issue every few seconds costs nothing while nothing is happening — only a poll that finds a new comment spends quota, and that is a turn. `x-poll-interval` is obeyed when GitHub sends it.

  It is cheaper as well as faster: Actions bills per job and rounds each one up to a whole minute, so eight turns as eight runs cost dozens of rounded-up minutes where eight turns in one held job cost one rounding. `timeout-minutes` is 25 rather than the 360 default, and `wait` gives up after five minutes of silence — their next comment picks the conversation up where it stopped.

  Both surfaces are the same channel. The dashboard already posts comments on the issue as the signed-in person, so answering there and answering on GitHub are the same act and there is one source of truth; the dashboard shows whether a job is listening, because a reply answered in seconds and a reply that wakes a run are different experiences. A comment on an item whose conversation is being held is deliberately not requeued — the held job answers it, and starting a second conversation would ask the person the same question twice.

  `factory-role-brainstorm` is its own workflow rather than part of triage, for a reason worth keeping: triage starts the sandbox because it reproduces bugs, and that needs `FACTORY_SANDBOX_ENV`. A role whose whole job is talking to somebody should never be handed the app's secrets. It is the one role with a token during the run, because a question posted after the run has ended is not a question — scoped to issues and the factory's own data, and the agent never posts anything itself: it calls `bsf brainstorm say`, which redacts the text, strips `@` mentions and removes the factory's own markers before anything is sent.

- **Every role reads the conventions the repository already keeps for agents.** `AGENTS.md`, `CLAUDE.md`, `CONVENTIONS.md`, `.cursorrules`, `CONTRIBUTING.md`, `STYLEGUIDE.md`, `.claude/skills/` and anything the policy's new `prose.targets` names. Until now a role read `.factory/definition/context/` and nothing else, so a repo whose house style was written down had that file ignored by every build while the factory consulted its own paraphrase, written once at setup and stale ever after. `bsf repo-prose` resolves them on every run — nothing is recorded at setup, so a file added today is read today — and `fundamentals.md` is now for what the setup agent worked out from the code and found written down nowhere. Never anything under `.factory/`, `.github/workflows/` or `.git/`: that is the text that governs the roles.
- **Hardening can write a practice down, as a fourth lever.** Some corrections have no mechanical home — vernacular, register, which of two acceptable patterns a team prefers — and a rule for those is either unwriteable or so crude someone disables it within the week. Hardening may now write one into the repo's own conventions, where every role and every human contributor reads it. It is not equal to a static rule, a verification requirement or a refactor, because it is the only lever that cannot prove itself, so three conditions are gates rather than advice: the PR says why the other three cannot carry it, lists at least two instances under a `## Why a practice` heading (one instance is taste, and taste in a file every run reads is taste the whole repo inherits), and replaces rather than appends. Off unless the policy grants `prose` to hardening, so a factory installed before the lever existed does not start editing `AGENTS.md` on the strength of an upgrade; `harden-context` tells the hardener which it is, so a refused change costs no model time.
- **A budget on always-loaded prose.** `AGENTS.md` and its kind are in every build's and every gardening run's context, so a line there is paid for on every run for as long as the repo exists — and the cheapest thing an agent can do is append one more. The static gate now fails a file over 16 KiB (`prose.budget_bytes`), which forces consolidation instead; files read on demand have no budget. `bsf prose-budget` is the same check on its own.
- **A shared dashboard.** One static site on one domain instead of a copy per repository: sign-in with a link that opens GitHub's token form already filled in, `?repo=owner/name` links, a demo mode on a made-up factory, a note on empty pages that says whether the repository has no factory or has one that has not run yet, and a content security policy so the page can only talk to itself and `api.github.com`. `bsf dashboard-link` prints the link for a repository.
- **Sign in with GitHub.** One button instead of making a token: the person approves the Software Factory GitHub App at GitHub and lands back signed in (state and PKCE, tokens renewed in the background, no scopes beyond what the app was given). If the app is not installed on the repository the page says so, links to the install page and checks again. It runs through a Pages Function on the dashboard's own address (`functions/api/auth`, logic in `worker/src`), so there is no separate Worker to deploy and no cross-origin access; the standalone Worker and its OAuth-app flow are gone. The token form stays under "Use a token instead" and is the only way on a copy of the site without the function. `dashboard/scripts/app-link.ts` prints the GitHub App's registration link, filled in from the same permission list.
- A token with a missing permission is named at sign-in, and a refused action says which permission it needed.
- `npm run e2e` in the dashboard runs the built site in a real browser against a mocked GitHub API.

### Removed

- **The factory's own secret scan.** The scan workflow in this repository, its config, and the `gitleaks` entry in the eight language rule packs. Nothing ever ran the pack entry, and the workflow failed on a made-up key in a test. GitHub already scans every push to a public repository and blocks one that carries a secret.
- **The half-built self-improvement machinery.** `bsf benchmark`, the benchmark task and result schemas, the benchmark provider, the review's route to a definition change and its benchmark gate, the cost-vs-quality chart and the benchmark parts of the dashboard are gone, and `rubrics/definition.yaml` with them: `/practice` runs are no longer scored, and the review skips them. Automatic, measured changes to the factory's own definition are planned for v1.1 and will be redesigned. Kept: `/practice` (manual improvement through the `definition` pipeline), the scorers, the review and its record, and the `review_and_benchmarks` budget key (now labelled "Reviews and practices"). No installed factory exists yet, so nothing needs migrating.

### Changed

- **Line endings are fixed at LF.** `.gitattributes` stores and checks out every text file with LF, so a change made on Windows shows only the lines that changed.
- **One script for the lock hash.** `node scripts/lock-hash.mjs --write` rewrites the prompt fingerprint in a compiled role after a prompt edit; without `--write` it checks. A pull request now has to carry the compiled roles itself: the compile check fails when they differ from what the compiler produces, and nothing is committed to `main` after a merge.
- **One conflict rebuild at a time.** When main moved under several PRs that touch the same file, every one of them was rebuilt at once — against the same main, so each new PR was clean against main and conflicted with its siblings, and the first to merge sent the rest back for another rebuild. Five PRs on one file could cost twenty builder runs. Rebuilds now go out oldest first, one per scan, and every other conflicting PR carries a check saying how many are ahead of it and why. The queue drains itself, because a rebuild that lands is a push to main; `factory-conflicts` also runs when `factory-run` completes, for a rebuild that fails or escalates and so makes no push. No timer: an idle factory runs nothing extra, where an hourly scan would spend a fifth of a month's free Actions minutes finding nothing.
- **A problem the review saw once is watched, not hardened.** Every problem the review found became a guardrail, and a problem can be one scored failure in one run — so a single flaky dependency or odd issue could install a rule that every future change is judged against for years, on the autonomous path where nobody is asked. Twice is now the bar. The sighting is recorded against a stable problem id in the review's `unrouted` list (additive, optional `problem` field), and if the thing is real it recurs and the next review routes it; only the rules that should never have existed are lost.
- **The review's timing.** The first review is never skipped for too few runs: it is due 3 days after the factory's first graded run, if at least one run exists. Later reviews are skipped under 5 runs (was 10). The 50-run early trigger applies to both.
- **Hardening cannot feed itself.** Every review problem routes to hardening, except failures found in hardening runs: those are recorded as `unrouted` in the review record (additive, optional), shown on the Improvement page, and file no new work.

### Fixed

- **`factory/pr-report` no longer fails a PR that has its proof.** A pull request arrived carrying a 19.7 MB recording of the feature working, and the check on it said *"The PR does not show its proof"* — the recording had been dropped for being over an 8 MB encode target, with no ffmpeg on the runner to shrink it, so the single most valuable thing on the PR was gone. Listed beside it, under the heading "What is missing", was `summary line 1 was shortened to fit (282 → 200)`: something the tooling had done successfully. Three changes. **ffmpeg is installed** before a report is stored, when and only when there is a recording to process, so the degradation usually does not happen at all. **A report's notes are kept apart from its failures**: proof that is present and diminished — stored at full size, no preview, a line shortened — is said on the check and never fails it, while the report naming a file nobody wrote still does. And **a recording over the encode target is stored as it was written** up to the 10 MB hard cap, instead of being dropped; that cap was two different numbers in two files, and is now one.
- **You can see what the correction hook sent from your machine.** It read what you type at an agent in your own session and turned it into a work item in a repository, while the local record held sha256 hashes and nothing else — enough to stop the same correction going twice, no use at all for answering "what left my machine" without going and reading that repository's issues. The cache now keeps when, where and what, `bsf local-hook --sent` prints it, and an existing install's hash-only file is still read so its dedupe survives.
- **Mining says whether a correction is about your repository or about the factory.** "Use the api client, not fetch" is this codebase's convention and a guardrail here is right; "the proof is a screenshot of the title page again" is a factory defect, and a local guardrail for it is a private patch for a bug every other factory has. Each mined candidate now carries `target` (additive, optional). Nothing routes on it yet — it is recorded so history need not be re-mined when something does, and so a column of candidates marked `factory` is visible as what it is: a list of bugs somebody is working around.
- The dashboard's GitHub client called the browser's `fetch` as a method of itself, which browsers reject with "Illegal invocation", so a real sign-in could not have worked. The unit tests used a stand-in fetch and never saw it.

- No YAML for users. The Factory page now has a control for every setting a person may change (monthly budget, the three shares, merge-by-itself for each pipeline, cleanup PRs per night, cleanup hour), a list of who can start work, and an Ask the factory box. Saving a setting is one step: the dashboard opens a pull request labelled `factory:settings`, waits for `factory/policy`, and merges it as the signed-in person. The policy check counts that author as the approver only when they hold write access, the PR touches nothing but the settings file and the cleanup workflow's cron line, and every key it moved is on the list with a value the list accepts; anything else still needs a second approval. `bsf settings` shows and changes the same settings for the setup skill, keeping the file's comments. An issue labelled `factory:ask` is kept for the setup skill, with no work item or run. User-facing messages no longer name a file to edit, and a test fails if one does. Also fixed: the dashboard's polling hook re-requested on every render.
- Chief of staff. Each accepted request from a person is routed by one tool-less model call (`models.chief_of_staff`, default `claude-haiku-5-5`, charged to the budget) to product work, hardening or gardening, with a specific goal and a success check the verifier can test; one question at most when it is genuinely unclear. Trust stays deterministic, the request is treated as data, and a failure, a missing `ANTHROPIC_API_KEY` or a paused budget falls back to the old table. The decision and reason are on the work item (`success_check`, `routing`, additive and optional) and in the acknowledgement. People can move a request in one click on the dashboard (recorded, with a mis-route tile), and set standing goals on the Factory page or with `/focus` in a comment (`standing-goals.json`); the spec, gardener and hardener read them as tie-breakers. Role prompts are not rewritten and no role's frontmatter changed.
- Easier kickoff. Four issue forms (Feature, Bug, Harden this, Tidy this) install under `.github/ISSUE_TEMPLATE/`; the harden and tidy forms apply `factory:harden` and `factory:tidy`, and a tidy request goes to gardening. Each form and the dashboard's new **New request** button (on every page) ask for a goal, kept on the work item as `goal` (additive, optional) and used by the spec as the success check. Intake comments on an issue as soon as it has read it: the kind of work, the goal, and how an untrusted author's request gets started. Home has an answer box for the one question triage asks before a run, and shows how long it has waited; a question never times out or escalates. On an empty factory Home offers a first request from `.factory/first-request.json`, which setup writes and phase 7 smoke-tests.
- Automatic hardening from every correction. A trusted person's PR review comment, change request or push to a factory branch, or a correction in a local Claude Code session, becomes a hardening work item at once (no threshold, no label), linked to the corrected run (`human_corrections`, additive). Duplicates fold; comments on hardening or definition PRs are revisions, not corrections. The hardener now chooses among a static rule, a stronger verification requirement, and a refactor, equally, and no longer writes prose context. `bsf local-hook --install` adds the local capture hook to personal settings. Guardrails shows each change with its correction; Home shows candidates with Accept/Reject. The scheduled review's definition route is off until v1.1; `/practice` is unchanged.
- Videos on PRs by default. The verifier records one screen session with a chapter per acceptance check; the runner re-encodes it to a small MP4, makes an animated GIF preview (sped up, not cut, when long), moves the original out of the media ref, and enforces per-clip and per-PR size caps. GitHub cannot play repo-hosted video, so the PR shows the preview linking to the file and the dashboard plays the real one. The spec declares `ui_change` (additive, optional); product work that touches the UI fails the `factory/pr-report` check without a video.
- `bsf doctor` — what is wrong with an installed factory, changing nothing.
  The diagnosis the setup skill's repair mode does before it touches anything.
- `bsf contribute-corrections` — a teammate adds the corrections from their own
  machine. Two steps on purpose: the first writes a file and submits nothing,
  so they can read and prune what would be shared before it goes.
- `bsf consistency` — cross-artifact checks: environment variables against
  `.env.example` in both directions, README commands against the manifest's
  scripts, declared dependencies against the lockfile.
- `bsf migrate` and `bsf schema-surface` — the schema freeze. An additive
  change passes; a breaking one fails and asks for a major bump with a
  migration.
- `bsf dashboard` — serves the dashboard from your own machine, loopback only.
- Data-flow rules (Semgrep taint) in the TypeScript and Python packs.
- Rust, C#, Ruby and polyglot-monorepo fixtures; Rust, C# and Ruby rule packs.
- Human interactions per PR, on the dashboard and in the rollup.
- The Improvement page: review results, scorer pass rates, and cost against
  quality for every configuration benchmarked.
- The repository's own CI: typecheck, lint, tests, the schema surface, and the
  gates run for real against the fixtures.

### Fixed

- Every GitHub API request with a body was sending an empty one.
  `promisify(execFile)` ignores an `input` option, so `gh api --input -` waited
  on a stdin nobody wrote. `reportCheck`, which is how every gate tells GitHub
  its verdict, had never worked.
- A baseline entry was read as a per-file map in two places, so the gardener
  filed items asking an agent to clean files called `count` and `by_file`, and
  never skipped a retired rule.
- The merge queue had its own review mapper writing the wrong field names,
  which silently disabled the stale-approval check where merging is decided.
- Three bare `require()` calls in ESM modules, each of which threw only on the
  code path that reached it.
