Phase 1 sketch, 25 November 2026. Synthetic data: an invoicing app called Ledgerline, one morning.

The factory's dashboard, three ways. I recommend the Briefing.

The dashboard is where the owner spends almost all of their time with the factory, so the recommended direction is built out as the whole product: every page, every state, and every action the owner would otherwise open GitHub for. The other two directions are drawn at their core screens, so the comparison is about structure, not finish.

A. Briefing

The home page is written, not tiled. It opens with a sentence that answers the first question outright (Six things need you.), then the second and third in smaller type. Items that need a person come first, the conversation with an open question above everything else, with a reply box right there. The pull request is the one dark, wide block on the page: a screening of the recording, with Merge beside it. A rail on the right holds what's running, what's next, the month's spend and the standing goal, so the page uses the whole screen while text keeps a comfortable line length. As the factory gets better the page gets shorter and calmer, down to Nothing needs you.

Behind it sit six pages, each a place you'd go on purpose: Requests (everything the factory was asked, by state, kind or text), one page per request with tabs for the conversation, the pull request, its runs and its activity, Runs, Guardrails, Spend and Factory (settings, goals, workflows, sandbox, people, health, installation). Search, under /, jumps to any of it or does any common action; whatever matches nothing becomes a new request.

The factory speaks in its own typeface, a serif, and you speak in the sans, so the conversation reads like an interview rather than a support chat.

Everything it does

Merge three ways, request changes, comment on the pull request or on one line of the diff, mark files viewed, close without merging. Answer the factory, agree to its playback or correct it. File a request of any kind, open an issue for one that came from Slack, close and reopen, add and remove labels, change priority, let someone new start, move a request to another kind of work, drop one. Re-run failed jobs, cancel a run, run any factory workflow by hand. Accept or reject a guardrail, add and remove standing goals, change all nine settings, switch repositories, sign in and out, choose light or dark. Every one of these is performed in a real browser by bundle/check-actions.mjs, along with a check that each kind of data appears where it should: 61 of 61 pass. COVERAGE.md maps each action to the client method it calls; three are new methods to add in Phase 2.

C. Reel

A screening room. The newest proof plays first and large, the title set in condensed type like a film credit, and Merge glows under it like a cue light. A ticker across the top carries the machine work. Decisions that need you sit in a rack below; the conversation slides in as a sheet.

Why the Briefing

It answers the three questions in order

The first sentence on the page answers is anything waiting on me; the rail answers what's happening now; Landed answers did it get done. B makes you read a list to find out; C answers a different question first.

It puts the unanswered question first

Nothing moves until a question is answered, so the reply box is on the home page. C, the most striking of the three, ranks a pull request above it.

It gets quieter on its own

Fewer items, shorter page, down to a sentence. B always looks like a full inbox; C has an empty stage.

Proof is still the loudest thing

The pull request is the only dark, wide block on the home page, and its page shows every proof block at full width in the author's order.

It's easy to learn

Six plainly named pages, one page per request, actions where you'd look for them, and search for everything else. Every action says what it did, and anything that can't be undone asks first.

It works from bed

On a phone the rail and the request details fold under the main column, the details collapse to one line, and dialogs become bottom sheets.

Styling decision for Phase 2: no Tailwind

assistant-ui for the conversation (its useExternalStoreRuntime takes turns[] as the message array, onNew posts the GitHub comment, and isRunning is bound only to a live conversation with an answer outstanding), styled with plain CSS: one token file of custom properties and a CSS module per component. That's how this sketch is written, so it ports directly. prompt-kit would bring shadcn/ui and Tailwind, letting a component library decide the styling of a design that rests on two typefaces and about a dozen colours.

Type and colour

Schibsted Grotesk for the interface, Newsreader for the factory's voice, both self-hosted from @fontsource-variable. Ultramarine marks what needs a person, green means done, red means stuck, and the screening is near-black in both themes. Text colours clear 4.5:1 against their backgrounds in both themes.
