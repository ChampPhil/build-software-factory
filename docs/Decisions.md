# Decisions

These decisions are settled: build to them, don't reopen them. The former open questions are resolved in the last section. If you hit a question these docs don't answer, flag it to Philip with options instead of deciding it yourself.

- Read alongside [Principles](Principles.md), [Pipelines](Pipelines.md), and [Architecture](Architecture.md).
- If a decision here seems to block the work, stop and raise it; don't route around it.

## Key decisions and rationale

The factory is an open-source skill that builds a factory into the user's own repo, running entirely on GitHub with nothing hosted by the maintainer.

| Area | Decision | Why |
| --- | --- | --- |
| Reuse first | Every part of the factory reuses a mature open-source tool, GitHub feature or standard when one fits the hard constraints, and is built custom only when none does. The full map of what's reused and what's custom is in [Architecture](Architecture.md) (Built on existing open source) | Less code to write, test and secure; users meet tools they already know |
| Product form | An open-source **skill** builds the factory. The factory's **definition** (config, policy, roles, context, rubrics, guardrails) lives as files in the user's repo; its **engine** (the `bsf` runner) is a dependency every workflow pins to an exact commit SHA. Upgrades arrive automatically as PRs opened by GitHub's Dependabot, which a trusted human approves with one click; they are never merged without that approval | A skill can't be always-on, but a repo can; the factory stays defined in code, while the gate logic stays deterministic code that agents can't edit. A self-applying upgrade would let one compromised release reach every user's secrets at once
| Runtime | **GitHub Actions** listens for triggers and provides compute. Agents run through **GitHub Agentic Workflows (gh-aw)**, GitHub's MIT-licensed framework for running coding agents in Actions: one gh-aw workflow per role, each a read-only sandbox behind a network firewall whose only way to write is checked "safe outputs". The agent CLI is the one the user picks (Claude Code, Cursor CLI, Kilo Code, pi, Hermes Agent), run as a gh-aw engine. The factory acts on GitHub as its own GitHub App, created during setup | Zero servers for user or maintainer; "any model, any harness"; the security-critical part (isolating agent writes) is code GitHub maintains, not code we write |
| Data storage | A **`factory-data` ref** (`refs/factory/data`, outside the branch list): one file per run and per work item + a rollup `index.json` | Runs never collide; the dashboard reads one summary, not thousands of files; refs outside `refs/heads/` don't trigger the team's `push` workflows, so factory writes never run their CI |
| Media storage | **Two tiers**: reviewed media (key screenshots, short clips, diagrams) copied to long-lived storage on a `factory-media` ref, size-capped and kept 12 months by default; full raw video and logs stay as expiring workflow artifacts | Artifacts and workflow runs expire (90 days public, up to 400 private); a run file must never depend on a workflow run still existing; media in git must not grow the repo forever |
| No YAML for users | Every setting a person may change has a dashboard control that saves in one step (a pull request opened and merged as the signed-in person); the policy check counts a trusted author's settings-only change as their approval, because GitHub will not let them approve their own. Anything without a control goes through "Ask the factory" (an issue labelled `factory:ask`, which no agent works on) and the setup skill makes the change, with `bsf settings` for a setting. A test fails on any user-facing text that tells someone to edit a file | The files stay as the stored, reviewable form; the person never needs to know their names. Counting authorship as approval is safe only because the list of settings is fixed and checked key by key |
| Routing requests | A **chief of staff** routes each accepted human request to product work, hardening or gardening and writes a specific goal and success check. It is one tool-less model call from intake, not a gh-aw role, because the pipeline must be known before dispatch and the call needs no repo access. Trust stays deterministic code; the request text is data; failure falls back to the fixed table. Every decision and reason is visible on the work item and one click changes it, and moves are counted | Fixed table routes by trigger, not by what the person meant; a wrong guess has to be cheap to see and undo |
| Standing goals | Set by asking (dashboard or `/focus`), kept on the data ref, read as tie-breakers only. Nothing rewrites a role prompt | A goal for this month should not permanently change a role |
| Dashboard | A **static app** (Next.js with static export) on Cloudflare Pages, reading the GitHub API from the user's browser; polls for live runs | Free at any scale; user data never touches maintainer servers |
| Dashboard writes | Toggles and approvals **commit to the factory's config files** | The UI is a view; the factory stays defined in code |
| Repo | **One public monorepo**: `/skill`, `/runner`, `/adapters`, `/rules`, `/templates`, `/schema`, `/dashboard`, `/worker`, `/docs`; MIT | Skill and dashboard share the schema contract; one place for stars and issues |
| Pipelines | **Three fixed pipelines** with fixed steps: product work, gardening, hardening | Predictable, easy to reason about, safe to self-improve |
| Self-improvement | **Two parts:** instrumentation traces everything continuously; a **scheduled review** every few days has scorers grade all recent work and route each failure. In v1.0 every failure goes to hardening; failures found in hardening runs are shown to a person, never hardened again. The factory definition changes only by hand (`/practice`); automatic, benchmark-tested definition changes are v1.1 | Can never rewrite its own process; hardening cannot feed itself |
| Hardening first | Every lesson goes through an ordered check, strongest fix first: (1) can the code change so the mistake is impossible? → API change; (2) can a script tell right from wrong without running the code? → static rule; (3) can running the code check it? → test or verification scenario; superseded in v1.0: three equal options (static rule, stronger verification, refactor removing the problem class), never a prose context line. The hardener agent chooses; the human can override in the PR | Code checks are reproducible; prose piles up |
| Agents | **Seven fixed roles** (triage, spec, builder, verifier, gardener, hardener, scorer) sharing one repo-level context; builder and verifier always separate; agents never hold a write token | One update reaches every agent; no agent grades its own work |
| Gates | Run **by the factory** in a job with no builder in it, never trusted from the agent; results are recorded per commit, so a commit is never checked twice. Tests can be rewritten or deleted in any pipeline, but only if the spec declared which existing tests change; new or changed behavior must come with tests (diff coverage ≥ 80%, the main check); total coverage may not fall more than a point below its highest; a skipped test counts as a suppression (reason required, counted, capped). Mutation testing on changed lines from v0.2, with each language's existing tool. Violation baselines use each linter's native baseline (for example ESLint's bulk suppressions) wherever one exists. The verifier and scorers judge test quality | An agent reporting "tests pass" isn't evidence |
| Control point | One, everywhere: a **human approves the draft PR** by viewing verification artifacts; per-pipeline auto-merge toggles, all three free to turn on | The reviewer judges outcomes, not code |
| Enforcement | Branch protection + required checks on main where the plan allows (see Free private repos); the factory only adds its checks and never removes the repo's existing rules. The factory merges its own PRs, and only after its gates pass. Human PRs run the deterministic gates (static rules, tests, coverage; agent verification only on request) and merge through the team's normal flow once those pass; where the repo already has a CI test check that runs on factory branches, the factory reads its result instead of re-running tests (running them itself after 15 minutes without a result). The factory also requires branches to be up to date before merging, so human PRs are re-checked against the latest main too. A `factory/policy` check that runs from main's copy of its workflow fails any PR that edits workflow or definition files until a trusted human approves, so no PR, a fork's included, can rewrite the gates that judge it. No CODEOWNERS: a path-policy gate, always loaded from main (never from the PR), decides what each pipeline may change. Product work and gardening may change code and tests; hardening may also add or tighten guardrails; the factory definition (pipelines, roles, context, model settings, gate workflows, the policy itself) changes only through a PR approved by a trusted human. Weakening a guardrail (removing or loosening a rule, raising a baseline) fails the gate unless a human approves; lowering a baseline or raising the coverage floor is allowed in any pipeline. All three pipelines stay auto-mergeable | Nothing reaches main without the gates; nobody quietly weakens a gate; human work isn't slowed or charged for agent checks |
| Merging | **GitHub's native merge queue wherever the repo qualifies** (org-owned public repos; private repos on Enterprise Cloud); elsewhere a **factory-run fallback queue (one approved PR at a time: update from main, re-run static rules and tests, re-run agent verification only if main's new changes touch the PR's feature folders, merge; works on every plan; runs on events, not a timer)**; conflicts → agent rebases using both sides' intent → re-clear → re-approve; contradicting intents → human | Catches both textual conflicts and combinations that break the app |
| Setup | Seven phases ([Setup](Setup.md)); **per-rule baselines**. The setup PR holds config, rules, workflows and mechanical autofixes only; the formatter lands as one whole-repo commit (listed in `.git-blame-ignore-revs`); every other fix is baselined and handed to gardening | Rules go in before cleanup; the skill session stays short; the setup PR stays reviewable and every real code change gets its own verified PR |
| Correction mining | Setup tries to catch every past correction: developers' past chats with AI coding agents (local transcripts for this repo, with permission, redacted), review comments, reverts, fix commits, bug history and prose rules, grouped into problem classes and turned into guardrail candidates | Years of corrections become guardrails on day one |
| Local work | PR-level capture is automatic; local agent sessions captured by **hooks** committed to the repo, secrets redacted. Each developer is asked once, on their own machine, before their sessions are captured; no answer means nothing is captured. Transcripts are never stored on a public branch: on a public repo, session capture needs the private data repo | Full visibility where possible without anything on developer machines; nobody's chats become public or captured without their own consent |
| Order after setup | Traces → scheduled review (first one three days after the first graded run) | You see scorers working early |
| Schema | **Versioned** and kept stable | Others will build on it |
| Routing | Minimal: triggers become one standard work item (a file on `factory-data`) mapped to a pipeline; not a designed component. Fingerprints only shortlist duplicates; triage decides | Avoids over-engineering; reworded duplicates are still caught, and "still broken" reports are never dropped |
| Who can trigger | Agent work starts only from trusted people (repo collaborators with write access). Trust belongs to people, never integrations: issues an integration's bot account creates (Linear, Sentry) wait like outside issues. Outside issues, comments and PRs wait until a trusted person labels them, and untrusted comments are stripped from prompts | In a public repo, anyone can open an issue, and anyone can trigger a Sentry error: prevents prompt injection and strangers burning the user's API budget |
| Trigger sources | GitHub-native triggers (issues, comments, PRs, schedules, the dashboard's run button) plus tools that create GitHub issues at no cost: Slack via the free GitHub app for Slack, Linear via its built-in GitHub Issues sync, Sentry via its GitHub integration. No custom webhook receiver | Zero cost to the maintainer; every request arrives as one kind of thing, a GitHub issue |
| Bot permissions | The factory's GitHub App gets admin permission (to sync config files into branch protection and repo settings) and no workflows permission (it can't edit `.github/workflows`). Each job mints its own down-scoped token with `actions/create-github-app-token`; only the settings-sync job gets admin. Agents hold no write token: they write only through gh-aw safe outputs, after gh-aw's threat detection, and gh-aw's firewall lets them reach only the model API and package registries | Settings stay defined in code; the bot can't tamper with its own gates; a hijacked agent can't weaken protection or exfiltrate much |
| Free private repos | Same factory, softer enforcement. The factory still merges only through its gates and its own merge queue, but humans can't be blocked from pushing to main, so a post-push audit re-runs the gates on every commit to main and flags anything that bypassed them on the dashboard, with an optional revert PR. Setup tells users GitHub Pro unlocks hard enforcement | Branch protection, rulesets and CODEOWNERS on private repos need a paid plan; GitHub's merge queue needs an org-owned public repo or Enterprise Cloud |
| Data privacy | Traces live on `factory-data` by default, with an option to store them in a separate private repo. Local session transcripts never go on a public branch: on a public repo they're stored only if the user picks the private data repo | In a public repo, everything in the repo, the factory's data refs included, is public too |
| Cost reporting | Every agent step reports tokens and cost, read from gh-aw's own session evidence first (its normalized `agent-session.jsonl`, then its API proxy's metering), then the harness's session log with memex, then priced with a LiteLLM table; `unknown` when none of them has it, never zero | Spending metrics depend on it; agents' own cost reporting is optional and uneven, and proxy metering does not depend on the agent telling the truth about itself |
| Harness integration | Built on existing open source, not five hand-written wrappers: harnesses run as gh-aw engines — built-in for Claude Code and pi, a gh-aw behaviour-defined engine definition for Kilo Code, Cursor CLI and Hermes Agent; past local sessions are read with memex; cost is priced with a LiteLLM table. All pinned to exact versions | One framework and one reader cover all five harnesses; less code to write and maintain. The caveat found during the build: a definition alone suffices only for a CLI whose headless mode emits clean JSONL — gh-aw's own third-party sample needed a 200-line harness script besides |
| Untested behavior | Gardening also scans recently merged behavior and adds tests or guardrail candidates wherever they're missing | Catches what slipped past the diff-coverage check |
| Role orchestration | Each role is a gh-aw **`workflow_call` reusable workflow** that `factory-run` calls as a job, sequenced with `needs:`; gate retries are `factory-run` re-dispatching itself per attempt. Not dispatch-and-poll | A job that waits for another workflow is billed for the whole wait, and `workflow_dispatch` returns no run id to correlate on. As jobs, the roles also make transcript isolation structural: the verifier's runner has no path to the builder's transcript |
| Sandbox posture is per repo, not uniform | Agents run in gh-aw's AWF sandbox on the default Docker profile. A repo whose app needs an Actions `services:` sidecar (a database) needs `sandbox.agent.runtime: docker-sudo-iptables`, which runs AWF with host privileges; setup detects this, tells the user their repo gets the weaker posture, and prefers starting the dependency inside the agent's network from `pre-agent-steps` where that works | gh-aw rejects published service connectivity on every other profile. Pretending the posture is uniform would hide a real difference in isolation between repos |
| Protected files, twice | gh-aw's own protected-file check stays on, and the factory's `factory/policy` path check stays on. Each role workflow gets a per-pipeline `protected-files` policy from its caller; only hardening excludes `.factory/guardrails/`, only definition PRs exclude `.factory/definition/`, and `.github/` is never excluded | gh-aw protects every top-level dot-folder by default, `.factory/` included, so hardening PRs would otherwise arrive carrying an automatic rejection. Keeping both layers is cheap and they fail independently |
| Recompiling lock files | A second **recompiler App** (`contents: write` + `workflows: write`, nothing else) runs `gh aw compile` in Actions and opens a PR that `factory/policy` gates. The skill's repair mode is the fallback for users who decline it | Compiled `.lock.yml` files live in `.github/workflows/`, which the factory App must never write. Splitting the credential keeps "neither App can both rewrite a gate and clear it" true, and stops lock files drifting because nobody ran the CLI |
| Pipeline coordination | Every pipeline reads a shared work ledger before starting: open PRs, in-flight runs and recent work on factory-data. It prevents duplicate work, not overlapping files: a new work item that matches an existing one attaches to it instead of starting a duplicate; gardening doesn't re-fix a violation an open PR already fixes; hardening checks for an existing rule or candidate first. Nothing is locked; overlapping changes are handled by conflict resolution and the merge queue | Prevents wasted, repeated work; locking areas would serialize the factory and can't work at scale, since agents don't know up front which files they'll touch |

## Non-goals for v1

These are deliberately out of scope; don't build them, and don't design in ways that require them.

- **Platforms other than GitHub** (GitLab, Bitbucket) → keep adapter seams clean, but ship GitHub only.
- **A hosted backend** of any kind: no maintainer-run servers, databases or queues (beyond the sign-in function that runs on the dashboard's own free Cloudflare Pages site).
- **True live streaming** of agent actions → polling every few seconds is the v1 experience.
- **Capturing human IDE activity** (keystrokes, local edits) → PR-level history is the human trace.
- **Self-improvement that changes pipelines, steps or guardrails** → only context and the model for each step.
- **Broad formal verification** → only targeted checks for critical logic flagged during setup.
- **Enterprise features**: SSO, multi-org admin, audit exports, paid tiers.
- **A configurable everything** → the factory is opinionated; prefer one good default over options.
- **A public, sign-in-free dashboard** for watching a factory work → a later addition.

## Hard constraints

These can't be traded away for convenience or speed.

1. **Zero ongoing cost to the maintainer** → static hosting and free tiers only; nothing that scales cost with users.
2. **The user owns all their data** → code, traces, artifacts and config live in the user's own GitHub; nothing passes through maintainer infrastructure.
3. **Secrets never leave the user's environment** → API keys live in repo secrets; transcripts and traces are redacted before they're stored.
4. **The factory is defined in code, and users never touch it** → every setting, rule, role and toggle is a versioned file in the repo; the dashboard and the setup skill make every change, as a commit with the person's name on it. A user is never told to open or edit a definition file.
5. **Nothing reaches main without passing the gates** → for agents and humans alike (humans get the deterministic gates; agent verification on request).
6. **Guardrails can't be weakened silently** → a deterministic gate blocks removing or loosening a rule, raising a baseline, lowering the coverage floor, editing undeclared existing tests or adding unexplained skips, unless a human approves; changes to the factory definition (including that gate) need a trusted human's approval, checked by the path-policy gate.
7. **Adapt, don't replace** → reuse the repo's existing tools (CI, linters, test frameworks, dev environment, tracker, review flow) before adding new ones.
8. **Harness- and model-agnostic** → no hard dependency on a single agent CLI or model provider.
9. **Open source** → skill, templates, schema and dashboard all public under a permissive license.
10. **Design around GitHub's limits** → artifact and workflow-run retention (90 days public, up to 400 private), and scheduled workflows disabled after 60 days of inactivity in public repos.
11. **Local sessions are private by default** → a developer's agent transcripts are captured only with their own consent and never stored where the public can read them.

## Resolved questions

Every former open question is now decided; only the domain name is still open.

| Question | Decision |
| --- | --- |
| Retry cap | 3 attempts per gate per work item, then escalate to a human with the full failure history |
| Agent CLIs | Supported by v1.0: Hermes Agent, Claude Code, Kilo Code, pi, Cursor CLI. v0.1 ships Claude Code; the other four arrive in v0.2 |
| Languages | Supported by v1.0: TypeScript, JavaScript, Python, Go, Java, Rust, C#, Ruby. v0.1 ships TypeScript, JavaScript and Python; v0.2 adds Go and Java; v1.0 adds Rust, C# and Ruby |
| Media storage | A `factory-media` ref holds long-lived assets (key screenshots, short clips, diagrams; at most 1 MB per screenshot, 10 MB per clip, 25 MB per run), kept 12 months by default and squashed monthly to drop expired media; workflow artifacts hold the long, complex verification artifacts (full videos, logs, raw runtime traces) and expire with retention |
| Dashboard sign-in | "Sign in with GitHub" (a GitHub App, through a Pages Function on the dashboard's own address) is the main way; a pasted fine-grained token, made from a link that fills in GitHub's form, stays as the fallback |
| Gardening schedule | Nightly; at most 5 PRs a night, each fixing one problem class (one rule or one principle), so every PR stays small |
| Baseline threshold | At setup, every rule with violations is baselined unless a mechanical autofix clears it (the formatter, a linter's `--fix`). In hardening, decided per rule: if the rule's existing violations fit in one PR (at most 25 violations across at most 20 files), fix them in the hardening PR; otherwise record a baseline and seed gardening items. Counts are stored per file |
| Scorer rubrics | One scorer per pipeline plus shared criteria: followed the intent, change is minimal, matches codebase patterns, tests are meaningful, artifacts prove the claim. Scores 1–5 with failure tags; rubrics are versioned files in the factory definition |
| Actions minutes and spend | Setup estimates monthly Actions minutes and model spend from recent repo activity plus nightly gardening and scheduled reviews; the budget has two limits, model spend and Actions minutes (defaulting to the plan's included minutes, none on public repos), both split into shares (default product work 60%, gardening 25%, reviews and practices 15%); *(changed 2026-11-21)* the dollar budget is a hard ceiling: each agent step reserves its worst case before it starts, gardening and review stay within their shares and product work may use the rest, never past the total; Actions minutes are left to GitHub's own Actions spending limit, which stops at the plan's included minutes by default. Nothing polls on a timer, so an idle factory costs close to nothing |
| Monorepos | One factory per repo, with a section per app in the feature map and runbook |
| Name | **Build Software Factory**; the skill is `build-software-factory`. Domain still open |
| Agent chat mining | Same five harnesses. A correction = a user turn that rejects or redirects the agent's work, or an undo of an agent edit. Setup lists the sessions for this repo and the user can exclude any before mining |
| Slack and Linear on free plans | Confirmed. Slack: the GitHub app works on the free plan (it uses 1 of the 10 free-plan app slots) and `/github open owner/repo` creates an issue. Linear: the free plan includes the GitHub integration, but caps at 250 active issues, and synced issues count toward that cap |
| Coverage tooling | Each language's standard tool, emitting LCOV or Cobertura: istanbul/c8 (JS/TS), coverage.py, go cover, JaCoCo, cargo-llvm-cov, coverlet, SimpleCov; diff-cover runs the diff-coverage check for all of them |
| Review cadence | Every 3 days; runs early once 50 factory runs pile up; skips if fewer than 5 runs happened since the last review. The first review is never skipped for too few runs: it is due 3 days after the first graded run if at least 1 run exists. `/practice` runs are not scored |
| When corrections start hardening | Every trusted correction starts hardening at once, from PR comments, change requests, pushes, and local sessions. No threshold, no label. Duplicates fold into the open item |
| Benchmark comparisons | *(removed from v1.0; planned for v1.1)* Each side runs 3 times on at least 10 tasks; a change wins only if its gain beats the run-to-run spread |
| Live view | The runner writes a small status file to a per-run `refs/factory/live/<run-id>` ref at each step change (deleted at run end); the dashboard polls it |
| Revert rate | Tracked from v0.1 (the dogfooding toggles depend on it) |
| Session capture | Off by default per developer: the hook asks each developer once, on first run on their machine, and stores the answer locally. Transcripts go only to a private data store (the `factory-data` ref of a private repo, or the private data repo); on a public repo with its data in the same repo, capture stays off and the dashboard says why |
